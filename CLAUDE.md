# Range

The user never writes code here; Claude does all of it and shows results as screenshots or builds on the phone.

- Text earns its place by saying something the screen can't: a rule that isn't visible, what happens before something is deleted, or a little warmth at moments that matter (a first empty screen, all done, after a workout). Cut text that repeats a label, describes what's visible, or tells you to tap the obvious button.
- Screens are built from Material 3 components (top bars, list items, chips, buttons, sheets, dialogs) so the apps feel native. `RangeTheme` sets Space Grotesk and the colours: Material You by default, the app's `RangeAccents` fallback otherwise, light/dark/pure black per the user's Appearance settings. Use `MaterialTheme.colorScheme`/`typography`, never hard-coded colours or fonts.
- Write a custom component only when Material has none (e.g. `RangeCheckbox`, `RangeStepper`), and put it in `range-ui`.
- Each app differs only by its accent (`RangeAccents`) and its screens. Page transitions come from `RangeTransitions`.
- No proprietary dependencies (Google Play Services, Firebase, analytics): the apps must stay F-Droid compatible.
- Timers and reminders use AlarmManager + local notifications, never push.
- New app: add `apps/<name>` with the `range.android.application` plugin; SDK levels and build settings live in `build-logic`.
- After any UI change, run `./gradlew :apps:<app>:recordRoborazziDebug` and look at the PNGs in `apps/<app>/screenshots` before calling it done. Every screen needs a screenshot test.
- Icons are Material Symbols (Rounded) only. Add the symbol's name to `range-ui/icons.txt` and run `python3 -I scripts/icons.py`; never hand-draw icons or add an icon library.
- Room schemas in `apps/<app>/schemas` are committed. Bumping a database version needs a migration, not a destructive fallback: users' tasks live there.
- Every user-facing string exists in English (`values/`) and Swedish (`values-sv/`). Shared strings live in `range-ui` with a `range_` prefix.
- Format dates and times through the app's formatter (e.g. Tasks' `TaskFormat`), never `DateTimeFormatter` directly: it combines the app language with the phone's region.
- A repeating task is one row that moves from day to day; never insert a row per occurrence. A task's times are reminders: progress is a tick count (`doneCount`), never per-time state.
- Finished days are logged in `completions`, one row per finished day, written only by `TaskRepository` alongside the task. It's history for listing what was ticked off on each day, not a task row: never schedule or tick from it.
- Every tick in the list offers Undo via a snackbar; keep that the one way to take back a tick from the list. Deleting a task has no confirmation but offers Undo the same way: its page hands the id to the list, which deletes it and can put it back with its history (`TaskRepository.delete`/`restore`).
- Tasks' backup file (`Backup.kt`) has its own shape and `FORMAT` number, like Lift's. Tasks' own settings live in `TasksPreferences` (when tasks without a time remind, 9:00 by default); changing it re-syncs every alarm.
- Backup's file picking, go-ahead and toasts are shared: an app passes a `RangeBackup` to `RangeSettingsScreen` and only turns its data into text and back.
- The task list shows one day at a time (`dayView` in Tasks). Future days list every repeat that falls on them as untickable previews, plus undated (Anytime) tasks, which show on every day until done; past days list what was ticked off on them, read-only. Keep that logic in `DayView.kt`, covered by `DayViewTest`.
- Lift: a workout's sets count only once ticked off, and Finish needs every set ticked; ticking an empty set takes the placeholder (last time's set, else the set above). At most one workout is in progress. An exercise's `Measure` (reps/time), `Load` and `perSide` decide its columns, best set (`Exercise.setOrder`) and volume. `Load` is only weights or bodyweight: a bodyweight set's weight is signed, + added and − help, so one ordering and one `AddedWeight` line cover plain, weighted and assisted work. Removing an exercise archives it, so past workouts keep it. Progress graphs, records and the finish screen's comparisons all pick their number per exercise through `progressMetric`/`recordMetrics` in `Progress.kt`; a first time is never a record. Built-in exercises are rows with a `key`, named in the app's language through `LiftFormat.BUILT_IN_NAMES` unless renamed. `BuiltInExercises.all` defines every one; only `BuiltInExercises.offered` (empty for now) is filled in on launch. v5 deleted the rest, or archived those a workout or template uses, so bringing one back means adding it to `offered` and un-archiving its row.
- Lift's rest stopwatch counts up from the workout's `lastSetAt`, set when a set is ticked. `WorkoutNotification` follows `LiftRepository.inProgress` and draws the notification from the data, never from calls at each change: the rest stopwatch between sets, or with the setting on, one for the whole workout with the next set (`upNext`), progress and a button that ticks it (`tickNext`). Its clock counts on its own, so it works with the app closed. Templates keep exercises and set counts only; the numbers come from last time as placeholders. Templates open as a read-only overview and are edited after tapping Edit, on their own page; a template needs at least one exercise to be kept (a new one left empty is discarded) (sets, replace, remove with Undo, reorder, add); the exercise picker serves workouts and templates alike through `PickTarget`, adding several or swapping one. Starting a workout always offers empty or a template.
- Lift's backup file (`Backup.kt`) has its own shape and `FORMAT` number, apart from the Room schema: when the data changes, bump it and keep reading older files. Deleting a set or removing an exercise offers Undo. The rep max calculator and every estimated max use `RepMax` (Epley), so they always agree. Lift's own settings live in `LiftPreferences` (keep screen on and the workout notification, both off by default).
- Notes: a note is a title with either text (`body`) or a checklist (`items`, JSON in the row, null for text). A note opens for reading (formatting shown, marks gone, items still tickable) and Edit opens it for writing; new notes start out being written. There is one + for new notes; a note becomes a checklist from inside it. Text is light Markdown kept as typed: `Markdown.kt` styles it in the editor with the marks dimmed (identity offsets, so the cursor never jumps) and in previews with the marks gone; the formatting bar and Enter-continues-a-bullet edit the text through it, covered by `MarkdownTest`. Notes save shortly after typing stops and when left; a note left blank is discarded, and the list never shows blank ones. Pinning doesn't change `editedAt`. Deleting hands off to the list for Undo, as in Tasks. Notes' backup file has its own `FORMAT`, like the others. Locked notes keep only `title` in the clear; `NoteRepository` stores their body and items encrypted in `secret` and only `reveal`s them while `NoteLock` is unlocked. `NoteLock` wraps a random note key with an Android Keystore key that needs the fingerprint/PIN prompt (framework `BiometricPrompt` with a `CryptoObject`, no extra library); one unlock lasts until the app is left (`MainActivity.onStop`), after open notes save through `beforeLocking`. An open locked note sets `FLAG_SECURE`. Backups unlock first and carry locked notes in the clear, marked to lock again on restore. Pictures are files in `NoteImages` (`<id>.jpg`, or `<id>.enc` encrypted for a locked note, resealed when a note is locked or unlocked), shrunk on the way in; a note lists their names, backups carry them whole, and `tidyImages` deletes files no note has once they're an hour old. Screens load them through `LocalImageLoader`, which screenshot tests fill with painted scenes. Shared text, links and pictures (`ACTION_SEND`) and the launcher shortcuts (`res/xml/shortcuts.xml`) each make a new note in `MainActivity`.
- Calculator: one page, one sheet. The sheet is the display: every line is a sum with its answer, = keeps the line and starts the next, so the sheet is the history; there are no saved sheets. The keypad writes into the line through `Keys` (operators with spaces, thousands grouped as typed, smart parentheses), holding the phone's keyboard back with `InterceptPlatformTextInput`; abc swaps to the keyboard for words, units and names. All maths is in `math/`, plain Kotlin covered by `SheetTest`: `Lexer` (numbers in the region's format, units and English/Swedish keywords; other words are labels), `Evaluator` (BigDecimal, Google-style %, units, `Rates`, dates), `Sheet` (names, `ans`, `sum` per block, equations), `Solver` (lines and parabolas exactly, anything else numerically between ±1 000 000), `ValueFormat`. Plain answers whose decimals would run on show as fractions (`Fraction.near`), and quadratics with fraction coefficients solve exactly, roots and all (`Exact`); the big display adds the decimal. An answer wider than half its row goes under the line (`AnswerLayout`). In landscape the sheet sits left and every function beside the keypad. A line with one "=" that isn't a new name is an equation in its first free single letter (x, y, z, n…); one solution becomes a name below, which a later equation may solve for again, unlike one set by hand. The only network use is `RatesStore` fetching the ECB's daily rates at most every twelve hours; `res/raw/ecb_rates.xml` is the offline fallback, and currency answers show ≈.

## Commits

Use Conventional Commits: `type(scope): summary`, lowercase, imperative, no trailing period, under 72 characters. Add a body when the why isn't obvious from the summary.

- Types: `feat` (something users notice), `fix`, `refactor`, `perf`, `test`, `docs`, `build` (Gradle, dependencies, signing), `chore` (anything else).
- Scope is the part of the repo the commit touches: an app's folder name (`tasks`, `lift`), `ui` for `range-ui`, `build` for `build-logic` and `gradle/`, `scripts` for `scripts/`. Leave the scope out for repo-wide changes, e.g. `docs: rewrite README`.
- One commit per scope where practical. A change to `range-ui` made for one app is still `feat(ui)`, with the app's own changes in a separate `feat(tasks)` commit.
- Release tags are per app: `tasks-v1.2.0`.
- Commits are the user's alone: no `Co-Authored-By` or other Claude attribution lines in commit messages or PR descriptions.

Examples: `feat(tasks): add week strip for browsing future days`, `fix(ui): keep checkbox ring visible in pure black`, `build: bump compose bom to 2026.09.00`.
